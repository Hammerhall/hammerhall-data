# hammerhall-data

Открытые наборы данных для кузен Hammerhall — Stream Forge, а дальше асинхронной, реактивной
и многопоточной. Сами данные лежат в **выпусках** (Releases) этого репозитория: в git их нет, чтобы
репозиторий оставался лёгким. Кузня скачивает нужный набор сама при первом обращении и сверяет
контрольные суммы.

## Наборы

| код | выпуск | что | объём | лицензия |
|---|---|---|---|---|
| `air` | `air-data-v1` | авиаперевозки: 73 аэропорта сети в 17 странах (в справочнике — 5 498 аэропортов мира), 135 571 рейс за два года, 8,5 млн броней, 18,4 млн билетов, 24 млн перелётов, 23 млн посадочных талонов; сезонность по регионам и праздникам | ≈ 790 МБ, 9 файлов TSV.gz | MIT © 2025 Postgres Professional |
| `sto` | `sto-data-v1` | магазин «Кременъ»: интернет-магазин электроники — свои склады и маркетплейс, 31 таблица (каталог, цены и акции, склады, заказы, платежи, доставка, возвраты, отзывы, сессии сайта); профили `full` (≈ 109 млн строк) и `small` (≈ 4 млн) | ≈ 1,5 ГБ, TSV.gz + архив `small` | MIT |
| `auc` | `auc-data-v1` | аукционный дом «Дом Одина»: шесть отделов, живые торги в зале и онлайн-торги по времени, 31 таблица (дом и правила, вещи и мастера, договоры, торги и лоты, ставки и поручения, счета, расчёты с комитентами, платежи, сайт и уведомления); профили `full` (≈ 135 млн строк) и `small` (≈ 1,3 млн) | ≈ 2,3 ГБ, TSV.gz + архив `small` | MIT |

Все наборы устроены по одному шаблону: у каждого — папка `<код>/` с генератором, паспортом, схемой и ожиданиями,
профиль `small` (≈ 1 %) рядом с `full`, одна сборка, одна проверка и один CI. Генератор `air` — импорт из выгрузки
демобазы: вход — снимок в выпуске `air-source-20250901` этого репозитория, его sha256 — в паспорте (см.
`air/README.md`).

## Раскладка

| путь | что |
|---|---|
| `core/` | ядро генераторов (Java 25, `io.hammerhall.data.core.*`): описание схемы, запись TSV.gz, манифест, самопроверки ключей и ссылок, агрегаты, ожидания (`freeze` / `check`), профили, командная строка `Cli`, проверка публичных имён; тесты ядра и общие тесты набора (`DatasetContract`) |
| `<код>/` | набор: `README.md`; `dataset.properties` — паспорт; `src/` — генератор (`io.hammerhall.data.<код>.*`) и его тесты; `schema/` — DDL, ER-диаграмма, поля; `expected/<версия>-<профиль>.json` — ожидания выпуска; `pg-check.sql` — контрольные запросы (если есть) |
| `build.sh`, `pom.xml` | сборка: `build.sh` — основная, без Maven; `pom.xml` (модули `core`, `sto`, `air`, `auc`) — для IDE и `mvn -o test` |
| `tools/check_data.py` | проверка скачанного выпуска любого набора (только стандартная библиотека Python) |
| `tools/compare_manifests.py` | сверка двух `manifest.json` (два прогона, две ОС) |
| `tools/pg-check.sh` | загрузка выпуска во временный Postgres 16 и контрольные запросы (Linux) |
| `tools/ci/` | шаги CI, вынесенные в скрипты: выбор набора по паспорту, входы, заметки к выпуску |
| `.github/workflows/data.yml` | один CI на все наборы: по тегу `<код>-data-v*` и вручную |

### Набор — контракт

* **Генератор** — пакет `io.hammerhall.data.<код>`: класс, реализующий `core.gen.Dataset` (код, название, версия,
  генератор, seed, период, схема, модули, агрегаты, SOURCE.md и LICENSE, входы; по желанию — свои поля манифеста,
  уровень и заголовок gzip), и `Main` — `Cli.main(new XxxDataset(), args)`. Команды (`generate`, `schema`, `verify`,
  `freeze`, `check`, `names`) у всех наборов одни — их даёт `Cli`.
* **Тесты** — `<код>/src/test/…`; среди них — наследник `DatasetContract` (одна строка): паспорт совпадает с
  генератором, схема в git — с описанием схемы, `small` проходит самопроверку и сверку с манифестом, ни в выпуске,
  ни в файлах репозитория нет внутренних имён платформы. Без него `build.sh` считает тесты проваленными. Значения
  полей, помеченных в схеме `verbatimSource()` (из внешнего источника как есть — не наши слова), проверка выпуска
  пропускает и пишет, какие; заголовки, тексты, прочие поля и репозиторий проверяются всегда.
* **Паспорт** `<код>/dataset.properties` — строки «ключ=значение»: `code`, `title`, `summary`, `version` (она же
  тег), `license`, `build` (`java` — собирает CI), `profiles`, `release.environment` (`<код>-data-release`),
  `full.xmx`, `full.budget_minutes`, `inputs` и у каждого входа `input.<имя>.file`, `input.<имя>.release` или
  `input.<имя>.url`, `input.<имя>.sha256_tsv` или `input.<имя>.sha256`. Образец — `sto/dataset.properties`.
* **Входы** — путь к входу `<имя>`: `--<имя> ПУТЬ` → `-D<код>.<имя>=…` → переменная `<КОД>_<ИМЯ>` →
  `<код>/work/<файл>` (папки `work/` в git нет).

Новый набор — новая папка по этому образцу (и строка `<module>` в `pom.xml` — только для IDE); ядро, `build.sh`,
`tools/` и CI не меняются.

## Сборка

Нужны JDK 25 (`JAVA_HOME`) и bash: на Linux и macOS — свой, на Windows — Git Bash. Python для сборки не нужен.

```bash
mvn -B -q -pl core dependency:resolve      # один раз: JUnit 5 — в ~/.m2 (или любым другим способом)
./build.sh sto                             # ядро + набор: собрать (предупреждения — ошибки), тесты ядра и набора
./build.sh sto compile                     # только собрать
./build.sh sto run generate --profile small --out sto-data-v1-small
./build.sh sto exec check sto-data-v1-small  # exec — без пересборки
```

`build.sh` кладёт сборку в `target/<код>/`, передаёт генератору папку набора (`-Ddata.dir`), на Windows сам
переводит пути (`cygpath`), ставит разделитель classpath `;` и берёт банки JUnit из `M2_REPO` или `~/.m2/repository`.
Переводы строк держит `.gitattributes` (LF везде) — без него `build.sh` в Git Bash не запустится. Maven:
`mvn -o test` из корня (в рабочей копии со старой раскладкой сначала удалите `sto/target/`: там остались классы ядра,
и Maven возьмёт их вместо новых).

## Состав выпуска

* таблицы — `*.tsv.gz`: UTF-8, табуляция, заголовок в первой строке, пустое поле — NULL;
* `manifest.json` — версия, число строк, контрольные суммы (`sha256` — файла, `sha256_tsv` —
  содержимого; тождество набора — `sha256_tsv`: байты gzip зависят от сборки zlib), модель отбора
  или параметры генератора;
* `SOURCE.md` — источник, что изменено против исходной выгрузки, поля таблиц;
* `LICENSE` — лицензия данных;
* у наборов из генератора — ещё `schema-tables.sql`, `schema-constraints.sql`, `load-postgres.psql` (загрузка в
  Postgres) и `schema.mmd` (ER-диаграмма).

## Проверка скачанного выпуска

Одна команда для любого набора — из репозитория на теге выпуска:

```bash
python3 -X utf8 -I tools/check_data.py ПАПКА_ВЫПУСКА        # Linux, macOS
py -3 -X utf8 -I tools\check_data.py ПАПКА_ВЫПУСКА          # Windows
```

Набор и ожидания скрипт находит сам: версия — из `manifest.json` выпуска, код набора — её начало
(`sto-data-v1` → `sto`), ожидания — `<код>/expected/<версия>-<профиль>.json` (нет профиля в манифесте — `full`).
Другой файл — `--expected ФАЙЛ`, `--no-aggregates` — только строки и sha256 (быстрее на `full`). Итог — «ВЫПУСК В
ПОРЯДКЕ» (код 0) или «ВЫПУСК НЕ СОВПАЛ С ОЖИДАНИЯМИ» (код 1) и что именно разошлось. То же генератором:
`./build.sh <код> exec check ПАПКА`.

Загрузка в Postgres — из папки выпуска набора с генератором:

```bash
psql -v ON_ERROR_STOP=1 -d БАЗА -f schema-tables.sql -f load-postgres.psql -f schema-constraints.sql
```

## CI (`.github/workflows/data.yml`)

* код набора — из тега `<код>-data-vN` или из поля «dataset» ручного запуска; задача «Набор» читает паспорт и
  отклоняет с причиной набор без генератора на Java, тег, не равный версии, неизвестный код;
* сборка и тесты на Ubuntu и Windows; схема в git сверяется с генератором; входы — по паспорту, с проверкой сумм;
* `small` дважды на каждой ОС — манифесты побайтно равны, внутренних имён нет, проверка против `expected/`,
  загрузка в Postgres; затем Linux ↔ Windows — тождество по `rows` и `sha256_tsv`;
* `full` на Ubuntu — время и пиковая память — в сводке; проверка против `expected/`;
* по тегу — выпуск GitHub после одобрения в окружении `<код>-data-release`: файлы `full` и архив `<версия>-small.tar`;
* ручной запуск — то же без выпуска, проверка справочно, новые ожидания (`freeze`) — в артефактах `expected-*`.
