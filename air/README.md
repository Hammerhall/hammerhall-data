# `air` — набор «Авиаперевозки»

Выпуск `air-data-v1`: данные авиаперевозок на основе демонстрационной базы Postgres Pro «Авиаперевозки» 2.0
(выгрузка `demo-20250901-2y`, MIT © 2025 Postgres Professional): 9 таблиц, ≈ 74 млн строк — аэропорты, самолёты и
места, маршруты, рейсы, брони, билеты, перелёты, посадочные талоны; сезонность по регионам и праздникам. Что
изменено против выгрузки и какие поля в таблицах — `SOURCE.md` выпуска.

Генератор здесь — **импорт**: вход — выгрузка демобазы, выход — те же таблицы, что у выпуска, собранного раньше
на Python и DuckDB: тот же вход даёт те же `sha256_tsv`. Устроен по общему шаблону наборов (см.
`README.md` в корне): ядро — `core/`, сборка — `./build.sh air`, проверка — `tools/check_data.py`, CI —
`.github/workflows/data.yml`. Java 25 без зависимостей (JUnit 5 — только для тестов).

## Сборка

Из корня репозитория; нужны JDK 25 (`JAVA_HOME`) и bash (на Windows — Git Bash).

```bash
./build.sh air            # собрать ядро и набор (предупреждения — ошибки) и прогнать тесты
./build.sh air compile    # только собрать
```

Тестам выгрузка не нужна: без неё вход — крошечная выгрузка, которую тест пишет сам (`TinyDump`). С настоящей
(`AIR_DUMP`, `-Dair.dump=…` у Maven или `air/work/demo-20250901-2y.sql.gz`) общие тесты собирают `small` из неё, а
`RealDumpTest` сверяет его со справочниками и счётом отбора опубликованного `air-data-v1` (если sha256 выгрузки — тот,
что в паспорте).

## Генерация

```bash
./build.sh air run generate --profile small --out air-data-v1-small --dump demo-20250901-2y.sql.gz
./build.sh air exec generate --profile full --out air-data-v1 --dump demo-20250901-2y.sql.gz --inputs strict
```

`--dump ПУТЬ` — иначе `AIR_DUMP` или `air/work/demo-20250901-2y.sql.gz`. `--inputs strict` — sha256 выгрузки обязан
совпасть с паспортом. `--seed N` (по умолчанию 20250901) влияет только на выборку `small`. `--gzip 1..9` — по
умолчанию 9: как у прежней сборки, и тогда при том же содержимом совпадают и байты файлов (заголовок gzip — как у
CPython). `--to` не принимается: окно задаёт выгрузка. Куча — `JAVA_XMX` (по умолчанию 4g), временные файлы —
`JAVA_OPTS=-Ddata.tmpdir=…`.

| профиль | что | строк | сжатого |
|---|---|---|---|
| `small` | брони — ≈ 1 % броней `full` (со всеми их билетами, перелётами и талонами); аэропорты, самолёты, места, маршруты, рейсы — целиком | ≈ 0,9 млн | ≈ 11 МБ |
| `full` | весь отбор модели | ≈ 74 млн | ≈ 790 МБ |

### Как устроен импорт

Выгрузка (`pg_dump` текстом, gzip, ≈ 1,1 ГБ; распакованная — ≈ 5 ГБ) читается потоком, на диск не распаковывается;
порядок блоков COPY и строк в них не важен.

1. **Первый проход** (`readInputs`): sha256 файла — в том же проходе; справочники и рейсы — целиком; у броней — число и
   последняя продажа; у билетов и перелётов — только ключи (номер билета, бронь, рейс) массивами `long`
   (≈ 16 байт на строку). Посадочные талоны не разбираются.
2. **Отбор** (`Selection`): рейс → версия маршрута → аэропорт вылета; первый вылет брони — поразрядной сортировкой и
   слиянием по номеру билета и брони; модель сезонности; для `small` — ещё отдельный хеш номера брони. Итог — два
   множества: брони и их билеты.
3. **Второй проход** (модуль продаж): строки броней, билетов, перелётов и талонов отбора — во внешнюю сортировку
   (отрезки по 1 млн строк на диск, deflate), затем слиянием — в файлы выпуска в порядке таблиц. Ссылки и ключи
   проверяет ядро на лету.

Запись — двумя дорожками (брони, билеты, перелёты | талоны): узкое место — gzip 9, у каждого файла свой поток.
`full` на 2 ядрах: ≈ 6,5 мин (первый проход ≈ 25 с, отбор ≈ 10 с, второй проход ≈ 1,5 мин, запись ≈ 4,5 мин),
куча — 4 ГБ, временных файлов — ≈ 1,1 ГБ (отрезки сортировки и отложенные ссылки талонов), удаляются по ходу.

## Что делает импорт с данными

То же, что SQL прежней сборки на DuckDB, один в один (сверено на снимке `air-source-20250901`: все 9 таблиц
совпали с первым выпуском `air-data-v1` по содержимому и по байтам файлов):

* время — секунды Unix, UTC: `epoch(x::timestamptz)::bigint` — **округление** к ближайшей секунде (половина — к
  чётной; так приводит `double → bigint` DuckDB), одно место — `PgValues.seconds`;
* брони отбираются целиком по модели сезонности (`Seasonality`; таблицы — те же, что в манифесте выпуска);
* справочник аэропортов — без нескольких аэропортов источника (`NetworkModule.EXCLUDED_AIRPORTS`); в сеть маршрутов
  они не входят;
* JSON-поля — на `_en` и `_ru`, координаты — долгота и широта, период маршрута — `valid_from`, `valid_to`, дни недели —
  без скобок, длительность — минуты; остальное — текстом как есть (деньги, числа);
* порядок строк — как в SQL сборки (у посадочных талонов — `flight_id, boarding_no` с NULL в конце, `ticket_no`).

Значение, которое в выпуске записалось бы иначе, чем в выгрузке (деньги не с двумя знаками, число не в канонической
записи), — ошибка, а не тихо другая запись.

Поля, чьё содержание взято из выгрузки без изменений (42 из 51: названия, города, страны, модели, коды, номера броней
и билетов, документы и имена пассажиров, места, классы, статусы, суммы), помечены в `AirSchema` `verbatimSource()`:
это не наши слова, и проверка внутренних имён выпуска (`names`, тест контракта) их значения пропускает, о чём пишет
строкой «значения внешнего источника как есть не проверялись: …». Заголовки, тексты выпуска, вычисленные поля
(моменты, минуты) и весь репозиторий проверяются как обычно.

## Тождество и проверка выпуска

Как у всех наборов (см. `README.md` в корне и `sto/README.md`): тождество — `rows` и `sha256_tsv` таблиц, поля
манифеста кроме списка файлов, тексты без сжатия, агрегаты. Проверка скачанного выпуска:

```bash
python3 -X utf8 -I tools/check_data.py ПАПКА_ВЫПУСКА        # Linux, macOS
py -3 -X utf8 -I tools\check_data.py ПАПКА_ВЫПУСКА          # Windows
./build.sh air exec check ПАПКА_ВЫПУСКА                     # то же — генератором
```

Ожидания — `air/expected/air-data-v1-<профиль>.json` (`freeze`). Загрузка в Postgres —
`psql -v ON_ERROR_STOP=1 -d БАЗА -f schema-tables.sql -f load-postgres.psql -f schema-constraints.sql` из папки
выпуска; проверка во временном Postgres 16 — `tools/pg-check.sh ПАПКА_ВЫПУСКА`.

## Новый выпуск

1. Снимок выгрузки — в выпуск `air-source-20250901` этого репозитория; её sha256 — в `dataset.properties`
   (`input.dump.sha256`) и в `AirDataset.DUMP`.
2. Изменили генератор так, что меняется содержимое, — новая версия генератора (`AirDataset.GENERATOR_VERSION`).
3. Ожидания: `./build.sh air exec freeze ПАПКА_SMALL` и `… freeze ПАПКА_FULL` (или ручной запуск workflow `data` с
   набором `air` — артефакты `expected-*`); схема — `./build.sh air exec schema`. Всё — в коммит.
4. Тег `air-data-vN` → CI собирает и проверяет; выпуск — после одобрения в окружении `air-data-release`.
