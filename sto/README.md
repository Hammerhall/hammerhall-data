# `sto` — генератор набора «Кременъ»

Магазин «Кременъ» (англ. Kremen) — синтетический интернет-магазин электроники и товаров для дома: свои склады (1P)
и продавцы маркетплейса (3P), Россия, рубли, период 01.10.2025 – 30.10.2027. Всё выдумано — магазин, бренды,
продавцы, поставщики, перевозчики, люди; города — российские города аэропортов `air-data-v1`. Набор — выпуск
`sto-data-v1` этого репозитория (31 таблица, ≈ 109 млн строк в `full`); здесь — генератор набора «Кременъ», из
которого он собран. Устроен по общему шаблону наборов (см. `README.md` в корне): ядро — `core/`, сборка —
`./build.sh sto`, проверка — `tools/check_data.py`, CI — `.github/workflows/data.yml`.

Генератор — Java 25 без зависимостей (JUnit 5 — только для тестов), MIT.

## Раскладка

| путь | что |
|---|---|
| `dataset.properties` | паспорт набора: код, версия, профили, вход (`airports.tsv.gz` из `air-data-v1` и его `sha256_tsv`), окружение выпуска |
| `src/main/java/io/hammerhall/data/sto/` | домен: `StoDataset` (контракт с ядром), `Main`, описание схемы `StoSchema`, модули (география, каталог, цены, поставщики, …) |
| `src/main/resources/io/hammerhall/data/sto/` | справочники мира (города, категории, виды товаров, характеристики) |
| `src/test/java/io/hammerhall/data/sto/` | тесты JUnit 5: общие тесты набора (`StoContractTest`), два прогона — один выпуск, продление периода, проверка выпуска, правила заказов и склада |
| `schema/` | DDL выпуска (`schema-tables.sql`, `schema-constraints.sql`), ER-диаграмма `schema.mmd`, поля `schema-fields.md` — генерируются командой `schema`; тест и CI сверяют их с генератором |
| `expected/` | ожидания выпуска по профилям (`sto-data-v1-small.json`, `sto-data-v1-full.json`) — для проверки скачанного выпуска |
| `pg-check.sql` | контрольные запросы для `tools/pg-check.sh` (цены без разрывов, ступенька НДС, смартфоны в продаже) |
| `pom.xml` | модуль Maven `sto-gen` (для IDE; сборка — `build.sh` в корне) |

Ядро (`io.hammerhall.data.core.*`: случайность от ключа сущности, календарь и налоги, деньги, описание схемы, запись
TSV.gz, самопроверки, выпуск, командная строка) — в `core/` корня, общее для всех наборов.

## Сборка

Из корня репозитория; нужны JDK 25 (`JAVA_HOME`) и bash (на Windows — Git Bash).

```bash
mvn -B -q -pl core dependency:resolve   # один раз: JUnit 5 — в ~/.m2 (или любым другим способом)
./build.sh sto                          # собрать ядро и набор (предупреждения — ошибки) и прогнать тесты
./build.sh sto compile                  # только собрать
```

Тестам нужен `airports.tsv.gz` из выпуска `air-data-v1`: путь — `STO_AIRPORTS` (или `-Dsto.airports=…` у Maven); по
умолчанию — `sto/work/airports.tsv.gz` (папка `work/` в git не попадает). Без него сборочные тесты пропускаются, а в
CI (`CI` задана) пропуск — провал.

## Генерация

```bash
./build.sh sto run generate --profile small --out sto-data-v1-small --airports air-data-v1/airports.tsv.gz
./build.sh sto exec generate --profile full --out sto-data-v1 --airports air-data-v1/airports.tsv.gz --inputs strict
```

`run` — собрать и запустить, `exec` — запустить собранное. Параметры: `--seed N` (по умолчанию 20251001),
`--modules a,b` (часть модулей — с зависимостями), `--to YYYY-MM-DD` (короче период), `--gzip 1..9` (по умолчанию 6:
на содержимое не влияет), `--inputs strict` (входы обязаны совпасть с эталоном `air-data-v1`), `--airports ПУТЬ`
(иначе — `STO_AIRPORTS` или `sto/work/airports.tsv.gz`). Куча — `JAVA_XMX` (по умолчанию 4g), временные файлы
проверок — `JAVA_OPTS=-Ddata.tmpdir=…` (по умолчанию системная папка).

| профиль | что | строк | сжатого | время |
|---|---|---|---|---|
| `small` | масштаб ≈ 1 % | ≈ 4,1 млн | ≈ 43 МБ | ≈ 40 с |
| `medium` | масштаб ≈ 10 % | ≈ 15,5 млн | ≈ 200 МБ | ≈ 1,5 мин |
| `full` | весь мир | ≈ 109 млн | ≈ 1,5 ГБ | ≈ 6 мин, ≤ 4 ГБ кучи на 2 ядрах |

Справочные таблицы (каталог, цены, склады и ячейки — ≈ 2,3 млн строк) одинаковы во всех профилях, поэтому `small` больше
1 % от `full`. Профиль — прогон в масштабе, а не вырезка: каталог, склады и календарь одинаковы во всех профилях, клиентов и заказов
меньше; идентификаторы между профилями не общие. Перед записью манифеста генератор проверяет себя: у каждой таблицы
— первичный ключ и UNIQUE, каждая ссылка, доменные инварианты модулей. Провал — манифест не пишется, выпуск не годен.

Другие команды: `schema [--out DIR]` (DDL, ER-диаграмма, поля — без данных; по умолчанию — в `sto/schema/`),
`verify DIR` (файлы против `manifest.json`), `names ПУТЬ` (нет ли внутренних имён платформы), `freeze DIR` и
`check DIR` — ниже.

## Тождество выпуска

Тот же seed и та же версия генератора — то же **содержимое** на Linux и Windows. Тождество — то, что от сборки
zlib не зависит:

* у каждой таблицы — число строк и `sha256_tsv` (sha256 разжатого TSV);
* поля `manifest.json`, кроме списка файлов (версия, генератор, seed, профиль, период, модули, входы, формат);
* sha256 текстов без сжатия: `LICENSE`, `schema-tables.sql`, `schema-constraints.sql`, `schema.mmd`,
  `load-postgres.psql`;
* контрольные агрегаты таблиц (суммы, минимумы, число NULL и т. п.) — показывают, *что* разошлось.

**Справочно** — байты и `sha256` файлов `.tsv.gz`, а с ними `manifest.json` целиком и `SOURCE.md` (размеры в нём —
по сжатым байтам). Сжатие — `java.util.zip` (zlib в составе JDK): одна и та же сборка JDK даёт одни байты, а другая
реализация zlib (например, zlib-ng) — другие байты того же содержимого. `sha256` сжатого файла сверяется с
`manifest.json` того же выпуска — это проверка скачивания, а не тождества.

## Проверка скачанного выпуска

Скачайте файлы выпуска в одну папку и проверьте их против ожиданий из репозитория (на теге выпуска), из корня:

```bash
python3 -X utf8 -I tools/check_data.py ПАПКА_ВЫПУСКА             # Linux, macOS
py -3 -X utf8 -I tools\check_data.py ПАПКА_ВЫПУСКА               # Windows
./build.sh sto exec check ПАПКА_ВЫПУСКА                          # то же — генератором (Java)
```

Ожидания берутся из `sto/expected/<версия>-<профиль>.json` (версия и профиль — из `manifest.json` выпуска), другой
файл — `--expected ФАЙЛ`. `--no-aggregates` (у Java — `--aggregates no`) — только строки и sha256: быстрее на `full`.
Итог — «ВЫПУСК В ПОРЯДКЕ» (код 0) или «ВЫПУСК НЕ СОВПАЛ С ОЖИДАНИЯМИ» (код 1) и что именно разошлось.

Загрузка в Postgres — из папки выпуска:

```bash
psql -v ON_ERROR_STOP=1 -d БАЗА -f schema-tables.sql -f load-postgres.psql -f schema-constraints.sql
```

Проверка загрузкой во временный Postgres 16 (Linux) — `tools/pg-check.sh ПАПКА_ВЫПУСКА` из корня.

## Новый выпуск

1. Изменили генератор — подняли его версию (`StoDataset.GENERATOR_VERSION`), если меняется содержимое; новая версия
   набора — `StoSchema.VERSION` и `version` в `dataset.properties` (тест контракта сверяет их).
2. Ожидания: `./build.sh sto exec freeze ПАПКА_SMALL` и `./build.sh sto exec freeze ПАПКА_FULL` (пишут
   `sto/expected/<версия>-<профиль>.json`) — локально или ручным запуском workflow `data` с набором `sto` (артефакты
   `expected-*`). Схема: `./build.sh sto exec schema`. Всё — в коммит.
3. Тег `sto-data-v1` → CI собирает и проверяет; выпуск выкладывается после одобрения в окружении `sto-data-release`.

Агрегаты для `freeze` — общий механизм: ядро добавляет к каждой таблице суммы денежных полей и число NULL
необязательных, модуль объявляет свои в `Module.aggregates()` (`Aggregate.sum`, `min`, `max`, `nulls`, `distinct`,
`count_eq`). Счёт — по тексту TSV, одинаковый в генераторе и в `tools/check_data.py`.

## CI

Общий workflow `.github/workflows/data.yml` (см. `README.md` в корне); для набора «Кременъ» — тег `sto-data-v*` или
ручной запуск с `dataset` = `sto`. Вход `airports.tsv.gz` CI берёт из выпуска `air-data-v1` и сверяет с паспортом.
